# 端到端工作流（W0–W6）：从题目到可验收提交包

> 本文件回答三个问题：**现在处于哪一阶段？下一步做什么？怎样才算过关（门禁）？**
> 核心纪律：**门禁未过，不进入下一阶段**。每个结论必须落到"文件 + 数值 + 复现命令"。

## 0. 阶段总览

| 阶段 | 目标 | 关键产出 | 门禁（Pass 才能进入下一阶段） | 常见坑（见 pitfalls.md） |
|---|---|---|---|---|
| W0 立项与指标 | 把"做对"定义清楚 | 指标口径表（数据集/容差/去重/统计方式）+ PC 基线 | PC 基线可一键复跑，指标口径写进文档 | — |
| W1 软硬划分 | 决定 PL/PS 边界 | 划分表（职责/依据/风险）+ MVP 范围 | MVP 能在纸面跑通、资源估算留 20% 余量 | — |
| W2 PL 实现 | 位流时序收敛 | HLS 报告 + Vivado 资源/时序报告 + 位流 | **WNS ≥ 0 且 0 失败端点**（或降频到达标） | P8、P18 |
| W3 启动链与固件 | 上电/下载后能跑 | FSBL/ps7_init/BOOT.bin/ELF/SD 布局 | 串口有启动头 + `image num` + 首帧正确 | P1、P2、P18 |
| W4 上板 bring-up | 单帧→全序列可跑 | 串口日志（含首帧、结束标记）+ 结果图 | 全帧无 `f_open`/打开错误、结束标记出现 | P3、P4、P5、P16、P17 |
| W5 量化验收 | 证明"跑得对/稳/快" | 五层验证表 + 性能表 + 证据路径 | 五层全过；指标口径与 W0 一致 | P7、P9、P10、P13、P14、P15 |
| W6 提交与复现 | 陌生人 30 分钟跑通 | 目录结构 + 自检脚本 + 最小复现路径 | 自检全过 + 陌生环境复跑通过 | P10、P11、P12 |

## W0 立项与指标定义（1–2 天）

**目标**：把"做对"变成可检验的定义，而不是"老师说差不多"。

1. 写清指标口径（缺一不可）：
   - 数据集：来源、帧数、分辨率、切面/类别；
   - 命中判定：预测/GT 坐标换算方式、容差公式（本工程：`max(w_px,h_px)/2 + 4 px`）；
   - 去重口径：同一帧内多少像素内算同一个位置（本工程：3 px）；
   - 统计方式：按类/整帧/总体，分母是 GT 点数还是帧数；
   - 频率/功耗版本：板级实测还是工具估算，必须分开标注。
2. 建立 **PC 基线**：同数据、同解码、同指标，能一键复跑（本工程 `sim/scripts/eval_pc_gt.py`）。
3. 初始化 `evidence.md`：先占位，后面每个数字填入证据文件。

**门禁**：换一个人按文档能复跑 PC 基线并得到同一数字（±0.1 pp）。
**AI 协作约束**：让模型只做"口径检查清单"，不要让它发明指标；所有口径由人确认。

---

## W1 软硬划分与 MVP（1–3 天）

**目标**：给出 PL/PS 划分表与最小可行版本范围。

1. 用 `prompt_workflows.md` 提示词 1 生成候选划分（要求表格：职责/依据/风险/验证方法）。
2. 人工按三条硬约束裁剪：资源、DDR 带宽、控制流复杂度。
3. 定义 MVP：先跑通"1 帧端到端 + 打印结果"，再做多帧与优化。
4. 记录风险及验证动作（每条风险配一个实验）。

**门禁**：划分表中每部分都有"为什么放这边"的依据；MVP 范围可在 1 周内跑通。
**AI 协作约束**：要求模型给出"反例"（什么情况下该划分会失败）。

---

## W2 PL 实现（1–3 周）

**目标**：位流时序收敛，资源有余量，报告可追溯。

1. HLS：目标时钟按 **10 ns（100 MHz）** 起步；先功能后性能（II/资源）。
2. 导出 IP → Vivado BD → 综合/实现；**每次实现记录位流 SHA256**。
3. 看三份报告：`report_utilization`、`report_timing_summary`、`report_power`。
4. 若不收敛：按"降频 → 加流水 → 改结构"顺序处理（见提示词 2），不要先怪工具。

**门禁**：WNS ≥ 0 且失败端点 = 0（或已明确降频并记录新频率版本）；资源余量 ≥ 20%（DSP/BRAM 尤其）。
**常见坑**：P8（定点格式）、P18（只换位流不改 FSBL/ps7_init → 假降频）。

---

## W3 启动链与固件（1–1.5 周）

**目标**：板子按预期方式启动并进入推理主循环。

1. 确定启动方式：JTAG 下载 / SD 卡启动（两者都建议保留，JTAG 便于调试）。
2. 启动链四件套对齐：FSBL、`ps7_init`、位流、应用 ELF。
   - **改频率/改 PS 配置后必须重导 HDF、换 `ps7_init`、重编 FSBL、重打 BOOT.bin**（P18）。
3. 文件系统注意：Zynq standalone 用 FatFS `f_open`，不要用 `fopen`（P1）；`SD_Init` 必须在所有文件操作前（P2）。
4. 串口协议：启动头（如 `image num`）+ 每帧结果行 + 结束标记（如 `ALL DONE`）。
5. SD 卡布局写进文档，并提供写卡脚本（含校验：bin 数 = img_num = png 数）。

**门禁**：上电/下载后串口出现启动头，且能读到 `image num`；卡内容校验通过。
**AI 协作约束**：改启动链的每一步都要能回滚；先备份旧 BOOT/ELF 再替换。

---

## W4 上板 bring-up（2–5 天）

**目标**：稳定跑完整个序列，日志/结果可信。

1. 顺序固定：**先开串口抓取 → 再下载/上电**（P16/P17）；抓取脚本要清缓冲并等启动标记（P4）。
2. 最小验证：单帧结果正确 + 单帧耗时合理；再跑全序列。
3. 异常处理：缺文件必须报错停止，不能继续算垃圾（P3）。
4. 每轮运行保存日志（文件名带时间戳），禁止覆盖旧日志。

**门禁**：全帧完成、0 个打开/读错误、结束标记出现、日志可回放；结果图与日志帧号一致（P14/P15）。
**常见坑**：串口截断帧（P16）、抓取太晚丢首帧（P17）、卡内容不完整（报 `rc=4`）。

---

## W5 量化验收（3–5 天）

**目标**：用五层验证证明"跑得对、跑得稳、跑得快"。

| 层 | 验什么 | 本工程做法 | 通过标准 |
|---|---|---|---|
| L1 权重 | 板端权重 = PC 折叠权重 | 逐层反量化对比，相关系数 | ≈1.000000 |
| L2 量化 | int16 仿真 vs float | 同一输入两边跑，比位置数/误差 | 位置数差 ≤5%，误差在容差内 |
| L3 板端 vs PC | 同一批输入的逐点误差 | 逐点距离统计 | 多数点 ≤2 px（本工程 96.7%） |
| L4 GT 精度 | 板端/PC 命中率 | 同口径评测 | 两者差 ≤5 pp；本工程 79.12% vs 77.88% |
| L5 确定性 | 断电重启/重复运行 | 两次日志逐行/逐值对比 | 差异为 0（本工程 1899/1899 逐位一致） |

性能与功耗口径：
- 帧时间：从固件计时或串口时间戳取平均，说明是否含 SD 读取/串口打印；
- 吞吐：`1/帧时间`，同时给 GOPS（`DSP 数 × 2 × 频率`）时注明理论值；
- 功耗：**Vivado 估算与板级实测分开写**，标注 vectorless/Confidence；
- 每个数字在 `evidence.md` 里填：数值、证据文件、复现命令、口径备注。

**门禁**：五层全过；指标口径与 W0 完全一致；报告中每个数字都能打开对应文件。
**常见坑**：P7（权重版本）、P9（类别数≠位置数）、P10（旧结果文件）、P13（解码类别归属）、P14（帧序）。

---

## W6 提交与复现（2–3 天）

**目标**：陌生人 30 分钟内能复现（至少能跑自检与样例）。

1. 目录结构按竞赛要求（本工程：`src/sim/build/board/data/skill/report` + README）。
2. 命名：纯英文小写（字母/数字/下划线/连字符），中文只在文件正文；运行时强制名（如 `BOOT.bin`）放 zip 内。
3. 提供两个自检：
   - `python skill/validation/check_skill.py`：技能包完整；
   - `python skill/validation/check_package.py`：提交包结构与产物、指标区间。
4. 写"30 分钟复现路径"：命令级，从解压到看到第一张结果图；大文件（>100 MB）走 Release。
5. 清理：删调试日志/重复渲染/临时目录，保留代表性证据（各项目 1–3 份）。

**门禁**：自检全过；按 README 在干净目录复跑一次成功；提交 zip 与仓库内容一致。
**常见坑**：P10（旧结果）、P11（Windows 编码）、P12（JTAG 识别）。

## 附 A：新增一条技能/踩坑的模板

```markdown
## P<n>. <一句话现象标题>

- **现象**：能看到什么（错误码/日志原文/数值范围）
- **触发条件**：什么操作/配置下出现
- **根因**：本质原因（不是表面现象）
- **排查步骤**：按顺序的实验，每步"看什么、期望什么、不符说明什么"
- **修复**：具体改法（文件/参数/顺序）
- **验证**：修复后如何确认（命令 + 期望输出）
- **关联**：相关条目/Prompt 编号
```

## 附 B：AI 编码代理协作约束（建议直接贴进系统提示词）

1. **一次只改一个变量**；每轮输出四栏：改动 / 预期 / 验证命令 / 实际结果。
2. 禁止"应该可以/看起来对"；结论必须引用日志行、报告字段或数值。
3. 报错先复述原始错误码与上下文，再给 2–3 个假设，按成本从低到高验证。
4. 涉及硬件动作（下载/复位/写卡/改启动配置）时，先给命令、回滚方式、验证点。
5. 任何"新经验"先写入踩坑模板，验证通过后再合并进技能包。
6. 不修改与当前问题无关的代码/显示效果；不虚构测量数据；估算值必须标注口径。
