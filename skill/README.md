# Skill Package：FPGA 视觉加速「上板 + 量化验收」通用技能包（v1.1）

> 从「YOLOv4-Tiny 超声散斑 36 关键点检测（Zynq-7020）」的完整实践中提炼，
> 面向**陌生队伍**与**AI 编码代理**：拿到本目录，可以按步骤复现同类 FPGA 视觉加速题的
> 划分、上板 bring-up、精度/性能量化验收与提交打包。

- 版本：v1.1（2026-11-02 结构重排 + 新增 workflow/evidence/check_skill）
- 适用平台：Zynq-7000 / Zynq MPSoC / PYNQ 类「PL 加速 + PS 调度 + 串口/文件输出」工程
- 关联：本工程同时提供**通用 PYNQ 技能包**（`pynq/README.md`），与本题无关，可单独复用
- 一句话：**"让板端结果可解释、可复现、可验收"**——不是教怎么写某个模型，而是教怎么证明硬件跑对了。

## 2. 拿到本包先看什么（按时间预算选）

### 5 分钟：确认"能拿来用"

1. 读本文件第 3 节「四个核心技能卡」，判断是否命中你的问题类型；
2. 跑一次技能包自检：
   ```bash
   python skill/validation/check_skill.py
   # 期望：ALL CHECKS PASSED（退出码 0）
   ```
3. 如果卡在具体现象上，直接查 `pitfalls.md` 的分类索引。

### 30 分钟：套到自己的题目

1. 用 `workflow.md` 的 W0–W6 对照自己处于哪一阶段，读该阶段"门禁"；
2. 开题/划分用 `prompt_workflows.md` 提示词 1；
3. 上板卡住用提示词 3（无输出定位）或提示词 7（频率生效核对），并对照 `case_templates.md` 模板 A/E；
4. 验收阶段用 `evidence.md` 的证据表结构，把每个数字都落到"文件 + 命令"上。

### 2 小时：从零复现本工程（可选）

按根目录 `README.md` 的「快速复现」执行；技能包只负责方法与验收，不重复工程文件。

## 3. 四个核心技能卡

> 每张卡固定六段：**触发条件 / 输入 / 步骤 / 输出 / 验证 / 失效条件**。
> 想新增技能时，复制这个格式（见 `workflow.md` 末尾模板）。

### 技能卡 ①：提示词工作流（Prompt Workflows）

| 项 | 内容 |
|---|---|
| 触发条件 | 需要 AI 帮你做方案取舍、定位疑难、设计验证方案，或要求它"别只给结论" |
| 输入 | 你的平台参数（LUT/DSP/BRAM/频率）、现象、日志片段、已排除项 |
| 步骤 | 选 `prompt_workflows.md` 对应模板 → 填【】→ 要求"表格 + 依据 + 风险 + 验证方法" → 对每条结论做最小实验 |
| 输出 | 结构化候选方案/排查清单/验证计划；每条都带可执行的验证动作 |
| 验证 | 任何一条建议必须能在 30 分钟内做一次小实验证伪；不做完不采纳 |
| 失效条件 | 纯软件/纯算法题效果打折；问题根因在硬件物理层（供电/接触）时提示词帮不上 |

### 技能卡 ②：端到端工作流（Workflow）

| 项 | 内容 |
|---|---|
| 触发条件 | 新题目冷启动，或项目进入新阶段需要知道"下一步做什么、怎么算过关" |
| 输入 | 当前阶段、已有产物（源码/位流/日志/报告） |
| 步骤 | `workflow.md`：W0 立项 → W1 软硬划分 → W2 HLS/Vivado → W3 SDK/启动 → W4 上板 bring-up → W5 量化验收 → W6 提交 |
| 输出 | 每阶段产出物清单 + 门禁结论（Pass/Fail + 证据路径） |
| 验证 | 门禁未过不进入下一阶段（这是防"带病往下走"的核心纪律） |
| 失效条件 | 无板卡/无 GT 的纯仿真项目可跳过 W3–W5 的板端部分 |

### 技能卡 ③：案例模板（Case Templates）

| 项 | 内容 |
|---|---|
| 触发条件 | 需要一份"照着填就能用"的检查表/评测表/报告表 |
| 输入 | 你的板卡、测试集、GT 格式 |
| 步骤 | `case_templates.md` 模板 A–F：bring-up、串口抓取、GT 评测、资源/时序报告、频率生效核对、提交合规 |
| 输出 | 填好的表格/清单，可直接进设计报告与答辩材料 |
| 验证 | 模板里每个"期望值"都要有来源（报告文件/日志行），不允许凭感觉填 |
| 失效条件 | 无串口/无 SD 的题目需替换传输通道（模板中已标注替换点） |

### 技能卡 ④：踩坑清单（Pitfalls）

| 项 | 内容 |
|---|---|
| 触发条件 | 出现异常现象（无输出、乱码、精度骤降、时序违例、频率不生效…） |
| 输入 | 现象、日志、硬件连接状态、最近改动 |
| 步骤 | 按 `pitfalls.md` 分类索引匹配现象 → 按"排查步骤"逐条验证 → 用"验证"一栏确认修复 |
| 输出 | 根因 + 修复 + 验证证据（不是"好像好了"） |
| 验证 | 修复后必须复跑原失败场景，并给出通过证据（日志/数字） |
| 失效条件 | 换平台（Kria/MPSoC）时部分条目（如 FSBL/ps7_init）需替换为对应启动链 |

## 6. 适用范围与失效条件

**适用**：
- FPGA/SoC 上部署 CNN/视觉算子，需要在板上验证"跑得对、跑得稳、跑得快"；
- 有 PC 参考实现（PyTorch/NumPy）可作为金标准；
- 板端通过串口/文件/SD 卡交换数据。

**不适用 / 需裁剪**：
- 纯仿真项目（跳过 W3–W5 板端部分）；
- 无 GT 标注的数据（技能卡 ③ 模板 C 的命中率部分改为"板端 vs PC 一致性"）；
- 无操作系统的裸机 PL 工程（`pitfalls.md` 的 FSBL/ps7_init 类条目不适用）。

## 7. 给 AI 编码代理的使用方式（摘要）

1. 先让代理读 `skill.json` + `workflow.md`，明确阶段与门禁；
2. 每次只改一个变量，要求代理给出"改动 → 预期 → 验证命令 → 实际结果"四栏；
3. 禁止接受"应该可以/看起来对"结论，必须落到日志行或报告数值；
4. 涉及硬件操作（下载/复位/改卡）时，先让代理输出命令并说明回滚方式，再执行；
5. 代理产出的每条"经验"先写进 `pitfalls.md` 模板，跑通验证后再合并。

## 9. 维护约定

- 任何新经验先落到 `pitfalls.md` 的模板（现象/根因/排查/修复/验证），跑通后编号；
- 数字类结论必须同时更新 `evidence.md` 的证据行；
- 指标口径变化（如去重半径、命中容差、频率版本）必须在 `changelog.md` 记录；
- 文件名保持纯英文小写（README.md 例外），禁止中文/空格。
