# ① 提示词工作流（Prompt Workflows）v1.1

> 每组提示词都经过本工程实际验证。用法：把【】里的内容替换成你自己的信息，整段发给大模型。
> **通用要求：输出结构化表格 + 依据 + 风险 + 验证方法，不要只给结论。**

## 使用约束（建议与提示词一起发给模型）

1. 一次只回答一个问题；先给 2–3 个假设，按验证成本从低到高排序。
2. 每条结论必须给"如何在 30 分钟内证伪"的实验（看什么文件/跑什么命令/期望什么值）。
3. 不允许"应该可以/一般来说"；不确定就写"不确定 + 需要什么信息"。
4. 涉及硬件动作时，先给操作步骤、回滚方式、验证点，再执行。
5. 输出里区分：**事实（日志/报告原文）** / **推断** / **建议**。
6. 不要发明数字；需要数字时给计算公式并标注口径（实测/估算/理论）。

## 通用系统提示词（会话开头贴一次）

```
你是我的 FPGA 视觉加速项目协作代理。项目状态：
- 平台：【Zynq-7020 / Zynq MPSoC / 其他】，工具链：【Vivado/SDK 2018.3】
- 当前阶段：【软硬划分 / 实现 / 上板 / 验收 / 提交】
- 已有产物：【位流/ELF/BOOT/日志/报告】
规则：一次只改一个变量；每个结论给"依据+风险+验证命令"；优先用现有文件里的证据；
      禁止编造测量数据；区分实测/估算/理论值。若信息不足，先列出需要我提供什么。
```

## 1. 软硬件划分（开题阶段）

```
我们在做【题目：XXX】，平台是【Zynq-7020 / Zynq MPSoC / 其他】，要实现【算法：YOLOv4-Tiny 卷积网络】。
已知：
- 模型规模：X 层、Y MACs、Z MB 权重
- 板卡资源：LUT/DSP/BRAM/DDR 带宽【数值】
- 实时性目标：≥ N FPS
请你：
1) 给出【PL 负责 / PS 负责】的划分方案，用表格列出每部分职责与理由；
2) 列出划分的 3 个主要风险（资源、带宽、时序）以及验证方法；
3) 给出最小可行版本（MVP）的裁剪建议（先跑通再优化）。
```

**本工程效果**：该模板帮助确认了"卷积层放 PL、解码/后处理放 PS"的划分；后续 ARM 端后处理只增加 2.0 ms，证明划分合理。

**失效条件**：模型带大量控制流/小算子时，PL 划分收益低，需改为"PL 只做热点算子"。

## 2. 时序违例定位（综合实现后）

```
Vivado 实现报告：时序 WNS = 【+0.336 ns】（100 MHz 收敛版，0 失败端点）。
HLS IP 的目标时钟是【10 ns】。资源占用：LUT 【82.67%】、DSP 【99.09%】、BRAM 【67.5%】。
请你：
1) 判断最可能的 3 个根因（按可能性排序），并说明如何在报告中确认；
2) 给出修复方案对比表（降频 / 加 pipeline / 改代码结构 / 改约束），包含对性能、资源、功耗的影响；
3) 给出修复后的验证计划（要看哪些报告、跑几次、怎么确认稳定）；
4) 特别说明：如果选择降频，除了重新实现位流，还需要同步改哪些启动链文件？
```

**本工程结论**：根因是"按 100 MHz 综合的 IP 跑更高频率"（HLS 目标 10 ns）；按目标频率重新实现后 WNS +0.336 ns、0 违例，帧时间 496.6 ms，精度不变（已验证）。
**附加教训**：降频不止换位流——还要重导 HDF、换 `ps7_init`、重编 FSBL、重打 BOOT.bin（P18）。

## 3. 板端无输出/卡死定位（上板阶段）

```
我们的 Zynq 板子烧录后：串口只打印【前 20 行】，然后【卡住 / 输出乱码 / 报错 XXX】。
已知：SD 卡里有【权重 42 个文件 + 测试图 50 张】；程序启动时先【初始化 SD】再【读权重】。
请你：
1) 列出排查顺序（从最可能到最不可能），每步给出"看什么、期望什么、不符合说明什么"；
2) 写出最小复现测试（只跑一帧/只读一个文件）的代码思路；
3) 给出常见平台陷阱清单（文件系统接口、缓存一致性、初始化顺序、路径写法）。
```

**本工程效果**：据此定位到 3 个真实 bug —— `fopen` 不可用（应改 `f_open`）、`SD_Init` 在读文件之后、读不到图仍继续计算产生垃圾点。

## 4. 精度回归排查（"结果突然变差"）

```
现象：同一权重、同一批输入，板端结果比 PC 参考差很多（GT 命中率【30% vs 78%】）。
已有信息：权重哈希【…】、输入哈希【…】、解码参数【conf=0.05,nms=0.3】、定点格式【int16, scale=512】。
请你：
1) 按"权重→输入→中间层→解码→显示"五层列出排查清单，每层给一个可执行的对比实验；
2) 判断哪些差异是量化可解释的（给出预期量级），哪些一定不正常；
3) 给出一个最小复现脚本的框架（读同一份数据，分别用两种路径跑，输出差值统计）；
4) 如果两边用同一份模型输出，但解码规则不同，如何验证是不是"类别归属"问题？
```

**本工程效果**：排除了"量化导致精度崩塌"；后续用同一份输出对比两种解码规则，定位到"每类独立 argmax 抢别类框"（P13），GT 命中 73.87% → 79.12%。

## 5. 结果可视化与对比分析

```
我们有【板端串口日志（每帧 36 个归一化坐标）】和【PC 参考结果】以及【原图】。
请你：
1) 给出"结果图"的绘制规范（框/点/编号/连线/统计信息），要求同时能看出"检测到几个不同位置"；
2) 给出板端 vs PC 的对比图设计（并排 / 差值热图 / 逐类命中率条形图），说明每种图能回答什么问题；
3) 给出一个可直接运行的 Python 脚本骨架（PIL/numpy，不依赖深度学习库）。
```

**本工程效果**：产出"去重位置数"统计口径 + 参考样式结果图，避免"36 类全画出来看着像 36 个点"的误读。

## 6. 提交前打包与复现自查

```
这是我们准备提交的工程目录【列出目录树】。竞赛要求：
- 目录/文件名纯英文小写（字母数字下划线连字符）；
- 提交内容：源码、仿真/验证结果、综合实现报告、上板工程与实测输出、构建脚本、技能包、设计报告。
请你：
1) 按提交清单逐项对照，指出缺失项与不合格命名；
2) 给出"陌生队伍 30 分钟复现"的最短路径（命令级步骤）；
3) 列出会阻止复现的 5 个最可能问题（路径硬编码、依赖缺失、二进制缺失、数据格式、权限）。
```

**本工程效果**：据此整理了本提交包结构，并发现"脚本内绝对路径"是最大迁移障碍（已改为包内相对路径）。

## 7. 时钟/频率是否真正生效（"假降频"排查）

```
我们在 Zynq 上把 PS 的 FCLK 从 【原频率】 改到 【新频率】 并重新实现了位流，
但板端每帧耗时仍然是 【原耗时】，和改之前一样（预期应按频率比例变化）。
已知：JTAG 下载用 ps7_init.tcl；SD 启动用 BOOT.bin(FSBL+bit+ELF)；板子能从串口输出帧耗时。
请你：
1) 列出 Zynq 的时钟配置链路（谁在什么时刻写时钟寄存器），解释为什么位流换了频率却没变；
2) 给出 3 个可在 10 分钟内完成的核对点（例如 ps7_init 寄存器值、FSBL 二进制、实际帧时间比值）；
3) 给出完整的修复清单（HDF/ps7_init/FSBL/BOOT.bin/JTAG 脚本，各自怎么改、怎么验证）；
4) 给出验证通过后的判据（帧时间应变成多少、允许的误差范围）。
```

**本工程效果**：确认 FCLK 由 FSBL/`ps7_init` 写 PS 时钟寄存器决定；修复后帧时间按频率比例变化，关键点结果逐位一致（P18）。

## 8. 上板失败的最小二分定位

```
现象：【板子能启动，但跑到第 N 帧报错/停止】（附串口日志关键片段）。
系统链路：SD 卡 → FatFS → 读图 → 权重 → PL 推理 → ARM 后处理 → 串口输出。
请你：
1) 把链路画成"可独立验证的 5 段"，每段给一个最小检查（读一个文件/跑一帧/只输出长度/回环一次）；
2) 给出二分定位顺序（先验证哪一段，为什么）；
3) 对每段给出"通过/不通过"的判据（具体输出/返回码/数值范围）；
4) 如果日志显示某帧文件打不开（FatFS rc=4），列出可能原因与对应验证方法。
```

**本工程效果**：用该思路把"跑到 frame 1 停止"定位到 SD 卡 `yolo_test` 内容不完整（`rc=4` FR_NO_FILE），而不是算法/时序问题。
